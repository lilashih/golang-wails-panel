# golang-wails-panel

`golang-wails-panel` is a desktop management tool built with Wails3, Go, and Vue 3. Its main purpose is to centrally manage projects, view application logs, and provide a stable operating interface through a desktop window.

This project currently uses the Wails3 architecture. The backend registers services through `application.Service`, and the frontend calls Go methods through Wails3 generated bindings.

## Main Features

### Project Panel

The project panel scans the project directory specified by `PROJECT_BASE_PATH`, reads the `project.json` under each subproject, and displays a list of manageable projects.

Currently supported operations:

- Read the project list and running status.
- Open the project folder.
- Start a project.
- Stop a project.
- Run install or dependency rebuild commands.
- Operation logs are written to log files and synchronized to the frontend live log panel.

The backend creates a runner based on the configuration in `project.json` that matches the current operating system. Platform differences for Windows, Linux, macOS, and others are handled by the backend, so the frontend does not need to determine the operating system.

### Log Viewer

The log viewer reads `.log` and `.txt` files under `storage/log`, and provides chunked loading and lookup capabilities for large files.

Currently supported:

- List log files.
- Set the current file.
- Read the beginning and subsequent content of files in chunks.
- Count the total number of lines.
- Search, filter, and highlight text.
- Tail follow, to track newly added content in the current log file in real time.
- Open the folder containing the log file.

### Development Guide

The frontend provides a README reader, which can retrieve the readable document list and content through backend APIs.

### Live Logs

The backend can write files and synchronize events to the frontend through `logger.Info`, `logger.Warn`, `logger.Error`, and `logger.Debug`. The frontend receives the `log` event through a global log store, instead of registering events repeatedly in each page.

## Backend Architecture

### `main.go`

`main.go` is only responsible for the Wails3 application startup flow:

- Register Wails3 event types.
- Create the backend app assembly object.
- Create the `application.App`.
- Register services.
- Configure the Wails3 logger.
- Configure embedded frontend assets.
- Create the main window.
- Start `app.Run()`.

Frontend assets are embedded in the following way:

```go
//go:embed all:frontend/dist
var assets embed.FS
```

### `src/app`

`src/app` is the Wails3 backend assembly layer, preventing `main.go` from directly depending on all business details.

| File | Responsibility |
| --- | --- |
| `app.go` | Create service instances and connect the Wails app with the event emitter |
| `services.go` | Wrap Go services as `application.Service` |
| `events.go` | Register Wails3 typed events |

Currently registered services:

- `PanelService`
- `AppInfoService`
- `LogViewerService`
- `ReadmeReaderService`

Currently registered events:

- `time`
- `log`
- `logViewer:tail`

### `src/core`

`src/core` contains shared capabilities across features, and does not contain business logic for specific pages.

| Directory | Description |
| --- | --- |
| `cmd/explore` | Open folders cross-platform |
| `cmd/shell` | Run shell commands cross-platform, timeout handling, environment variable enhancement |
| `config` | Load `.env` and default configuration |
| `def` | Shared formats and constants |
| `helper` | Helpers for paths, files, time, structure conversion, and more |
| `logger` | Daily logs, compression, frontend events, Wails3 slog adapter |

### `src/service`

`src/service` is split by feature package. Each service corresponds to a set of backend capabilities callable by the frontend.

When adding a new service, follow these rules:

- Add it under `src/service/<feature>`.
- Name the service type `Service`.
- If startup or shutdown lifecycle is needed, implement the Wails3 service lifecycle.
- Create the instance in `src/app/app.go`.
- Register it as `application.NewService(...)` in `src/app/services.go`.
- If events need to be pushed, inject them through a small interface or the app assembly layer, and do not let core modules bind directly to frontend pages.

Wails3 service lifecycle example:

```go
func (s *Service) ServiceStartup(ctx context.Context, _ application.ServiceOptions) error {
    s.ctx = ctx
    return nil
}

func (s *Service) ServiceShutdown() error {
    return nil
}
```

## Project Panel Configuration

### Project Directory

The project list is specified by `PROJECT_BASE_PATH`. The default value is:

```env
PROJECT_BASE_PATH=./projects
```

Path rules:

- Absolute paths can be used, such as C:\projects.
- Relative paths can be used, relative to the runtime base path.
- When `APP_MODE=release`, the runtime base path prioritizes the directory where the executable is located.
- Non-release modes use the current working directory, which is convenient for `wails3 dev` and IDE development.
- Regular folders and symlinks are supported.

### `project.json`

Each project folder must contain a `project.json`. This file must be in array format, and each configuration entry may correspond to a different operating system.

Required fields:

| Field | Description |
| --- | --- |
| `os` | Operating system, commonly `windows`, `linux`, `darwin` |
| `title` | Display name on the frontend |
| `key` | Unique identifier used by the runner to determine running status |
| `type` | Runner type, currently supports `pm2` and `exe` |
| `start` | Start command |
| `stop` | Stop command |
| `install` | Install or dependency rebuild command, can be an empty string |

Example shared configuration for Windows and Linux:

```json
[
  {
    "os": "windows",
    "title": "Nodejs project configuration example",
    "type": "pm2",
    "key": "my-node-app",
    "start": "pnpm start",
    "stop": "pnpm stop",
    "install": "pnpm install"
  },
  {
    "os": "linux",
    "title": "Nodejs project configuration example",
    "type": "pm2",
    "key": "my-node-app",
    "start": "pnpm start",
    "stop": "pnpm stop",
    "install": "pnpm install"
  }
]
```

`exe` type example:

```json
[
  {
    "os": "windows",
    "title": "Executable project configuration example",
    "type": "exe",
    "key": "app_windows.exe",
    "start": "start /B app_windows.exe",
    "stop": "taskkill /IM app_windows.exe /F",
    "install": "app_windows.exe migrate"
  },
  {
    "os": "linux",
    "title": "Executable project configuration example",
    "type": "exe",
    "key": "app_linux",
    "start": "nohup ./app_linux > ./app.log 2>&1 &",
    "stop": "pkill -f app_linux",
    "install": "./app_linux migrate"
  }
]
```

### Runner Behavior

| Type | Applicable Scenario | Running Status Detection |
| --- | --- | --- |
| `pm2` | Node.js, frontend services, resident services managed by PM2 | Run `pm2 jlist`, match `name == key` and status is `online` |
| `exe` | General executables or self-managed resident processes | Windows checks through task list; Unix-like systems check through process list |

Start and stop commands have a 30-second timeout. If the command itself is a resident service, it must background itself and exit, otherwise Panel will wait until timeout.

Recommendations:

- Windows resident startup can use `start /B ...`.
- Linux resident startup can use `nohup ... > app.log 2>&1 &`.
- The `key` for `pm2` must match the PM2 process name.
- The `key` for `exe` should be a recognizable process name, not just a display name.

## Logging System

### Log Directory

Logs are written by default to:

```text
storage/log
```

Filename format:

```text
log-YYYY-MM-DD.log
```

Log features:

- Automatically rotates files daily.
- When `LOGGER_COMPRESS=true`, expired logs are automatically compressed as `.gz`.
- ANSI color control codes are removed before writing.
- `logger.Log` is a wrapper around the standard library `*log.Logger`, so `log` methods and behavior can be used directly:
    - Methods such as `Print/Printf/Println`, `Fatal/Fatalf`, `Panic/Panicf` can be used directly.
    - It uses `flags` `log.LstdFlags | log.Lshortfile` by default (including timestamp and caller source file:line).  
- `logger.Info`, `logger.Warn`, `logger.Error`, and `logger.Debug` write files and push the `log` event to the frontend.

### Backend Usage

Write only to file:

```go
logger.Log.Println("Background task completed")
```

Write to file and synchronize to the frontend:

```go
logger.Info("Starting service: %s", name)
logger.Error("Startup failed: %v", err)
```

The Wails3 framework logger is connected to this project's logger through `logger.NewSlogLogger(slog.LevelInfo)`, allowing framework-level logs to enter the existing logging system as well.

## Environment Variables

Configuration is initialized by `src/core/config`. Default values are applied first, then `.env` is attempted to be loaded.

If `.env` does not exist, the program still starts with default values.

| Name | Default Value | Description |
| --- | --- | --- |
| `APP_ID` | `Panel` | Application ID, used by the fallback user configuration directory |
| `APP_NAME` | `Panel` | Application name |
| `APP_MODE` | `release` | Runtime mode, commonly `debug`, `release` |
| `APP_BASE_PATH` | `./` | Application base path setting |
| `PROJECT_BASE_PATH` | `./projects` | Project root directory scanned by the project panel |
| `PROJECT_JSON` | `project.json` | Project configuration filename |
| `LOGGER_COMPRESS` | `true` | Whether to compress expired logs |

Common local development `.env`:

```env
APP_MODE=debug
PROJECT_BASE_PATH=C:\projects
LOGGER_COMPRESS=false
```

### Wails3 Bindings

The frontend calls backend services through `frontend/bindings`. Using Panel as an example:

```ts
import {
  InstallProject,
  ListProjects,
  OpenProject,
  StartProject,
  StopProject,
} from "@bindings/gbase/src/service/panel/service.js";
```

Backend service calls should preferably be centralized in a store or API wrapper, and should not be scattered across many small components.

### Wails3 Events

The frontend registers events uniformly in `useWailsEvents.ts`:

```ts
Events.On("log", (event) => {
  logs.addLog(event.data);
});
```

Live logs are stored in `stores/logs.ts`, and pages and components only read store state.

## FAQ

### No projects are found after startup

Please check:

- Whether `PROJECT_BASE_PATH` in `.env` is correct.
- Whether the directory exists.
- Whether each project folder contains `project.json`.
- Whether `project.json` is in array format.
- Whether there is an `os` setting matching the current `runtime.GOOS`.
- Whether required fields `title`, `key`, `type`, `start`, and `stop` all have values.

### `pm2` status is always detected as not running

Please check:

- Whether the `key` in `project.json` matches the PM2 process name.
- Whether the runtime environment PATH can find `pm2` and `node`.
- The PATH obtained by a Linux desktop-launched application may be smaller than the terminal's PATH. This project enhances common PATH values on Unix-like systems, but if a special installation path is used, the environment should still be adjusted manually.

### Startup command timeout

The `start` and `stop` commands should exit after completing the startup or shutdown action. If the command itself is resident, please background it manually.

Windows example:

```cmd
start /B app.exe
```

Linux example:

```bash
nohup ./app > app.log 2>&1 &
```
